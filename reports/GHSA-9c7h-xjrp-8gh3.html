Stored XXE/SSRF/XSS via SVG upload sanitization bypass

XXE/SSRF/XSS CVSS 7.1 HIGH CWE-79: Cross-site Scripting snapotter-hq/SnapOtter ≤ 2.2.0

GHSA-9c7h-xjrp-8gh3 · CVE assignment pending (GitHub CNA)

Summary

Both upload routes — the standalone POST /api/v1/upload and the library POST /api/v1/files/upload — ran the SVG sanitizer only after the image validator had decoded the file:

// apps/api/src/routes/files.ts:117 (same shape at user-files.ts:337)
const safeBuffer = isValidImage && isSvgBuffer(buffer)
    ? sanitizeSvg(buffer)
    : buffer;

Because the routes accept any file type, an SVG that librsvg (via Sharp) cannot parse is stored anyway: a DOCTYPE declaring an external entity makes the parser fail, isValidImage is false, and the && short-circuit skips sanitizeSvg() entirely. The raw file is later served as image/svg+xml with its DOCTYPE, entity declarations, and any scriptable markup intact.

Two related weaknesses inside the sanitizer itself:

  • It stripped only unprefixed dangerous elements, so a namespace-prefixed survived even on SVGs the decoder accepted.
  • Its DOCTYPE-removal regex broke when a ] appeared inside a quoted entity value.

Impact

  • Stored XSS — an authenticated user who can upload files stores an SVG carrying active markup; a viewer who opens the stored SVG directly in a browser (or any surface that renders it inline) runs the embedded script.
  • Unauthenticated retrieval — the staged-upload download URL /api/v1/download/:jobId/:filename requires no authentication, so anyone with the job id can fetch the file.
  • Attack vector: network — upload as authenticated user, then victim interaction.
  • The chained file-read and request-forgery vectors from the original report did not reproduce in the shipped app: librsvg refuses to resolve the external entity (that refusal is exactly why validation fails), the tool routes reject invalid SVGs before processing, downloads carry Content-Disposition: attachment + X-Content-Type-Options: nosniff, and the response CSP allows no inline script — so a stored SVG does not execute as a document served from the app origin.

Root Cause

Sanitization was coupled to successful image validation instead of running on every SVG-bearing upload. The fix inverts the responsibility: both upload routes now sanitize SVG content regardless of whether the image decoder accepts the file, the sanitizer strips namespace-prefixed dangerous elements, and SVG detection plus DOCTYPE removal handle a prolog and quoted values.

Fix

Sanitize SVG uploads unconditionally — independent of the image validator — strip namespace-prefixed dangerous elements, and harden SVG detection and DOCTYPE removal:

// Both upload routes, after the fix:
const safeBuffer = isSvgBuffer(buffer) ? sanitizeSvg(buffer) : buffer;

Fixed in SnapOtter v2.3.0 (2026-11-03, also the project's one-million-pull thank-you release, which credits this report in the release notes). Advisory published 2026-11-03; CVE assignment pending.
